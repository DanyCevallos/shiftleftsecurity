02 — Definicion

Que es Shift Left Security?

Definicion 01

Shift Left Security es la practica de incorporar controles y revisiones de seguridad desde las primeras etapas del ciclo de vida del software, en lugar de hacerlo al final, cuando corregir un error cuesta entre 30 y 100 veces mas. El termino hace referencia a mover la seguridad hacia la izquierda en la linea de tiempo del proyecto.

— Seelam, J. (2019). Integrating Shift-Left Security in CI/CD.
Definicion 02

Segun la OWASP Foundation, el enfoque de seguridad temprana consiste en integrar pruebas, revisiones de codigo y analisis de amenazas dentro del propio flujo de trabajo del equipo de desarrollo, haciendo que la seguridad sea responsabilidad de todos y no solo del equipo de operaciones al momento del despliegue.

— OWASP DevSecOps Guideline v0.2

5 Principios fundamentales
01

Detectar antes, no despues

Un error encontrado durante el diseno tarda horas en corregirse. El mismo error en produccion puede tardar semanas y costar reputacion.

— Toner et al., 2025
02

La seguridad es parte del codigo

No se trata de agregar herramientas al final del pipeline. Cada linea de codigo debe escribirse pensando en quien podria abusar de ella.

— Malik & Prashasti, 2025
03

Automatizacion continua

Las pruebas SAST deben correr en cada commit. Si el equipo tiene que recordar ejecutarlas manualmente, eventualmente alguien se olvidara.

— Singh, 2019
04

Cultura sobre herramientas

Las herramientas no sirven si nadie les hace caso. Shift Left requiere que los desarrolladores entiendan por que hacen lo que hacen.

— Harness.io Blog, 2026
05

Responsabilidad compartida

El desarrollador que escribe el codigo es el primero responsable de su seguridad. QA y arquitectos son capas de respaldo, no los unicos responsables.

— Mohammed et al., 2025
03 — Problema

Que problema soluciona?

El codigo del Grupo 6 tiene un problema que parece pequeno pero representa una vulnerabilidad critica: las credenciales estan escritas directamente en el codigo fuente. Esto expone el sistema a multiples vectores de ataque de forma simultanea.

  • Acceso universal al repositorio

    Cualquier persona con acceso al repositorio tiene el usuario y la contrasena del sistema, incluso con permisos de solo lectura.

  • Bots automatizados en minutos

    Si el codigo se sube a GitHub sin proteccion, bots automatizados escanean credenciales hardcodeadas y las detectan en cuestiones de minutos.

  • Contrasenas en texto plano en los logs

    System.out.println("Login: " + user + " - " + pass) registra lo que el usuario escribe, exponiendo credenciales en archivos de log y consolas de servidores.

  • Contrasena trivialmente debil

    La contrasena "1234" no cumple ninguna politica de seguridad minima y es la primera que cualquier atacante intentaria en fuerza bruta.

  • Sin limite de intentos

    No hay ningun mecanismo de rate limiting, bloqueo de cuenta ni CAPTCHA. Un atacante puede intentar millones de combinaciones sin restricciones.

  • Como lo resuelve Shift Left

    Desde el Sprint 1 se establecen reglas que prohiben credenciales hardcodeadas y las herramientas SAST (SonarQube, Semgrep) las detectan automaticamente antes de que el codigo llegue a revision.

04 — Metodologia Agil

Relacion con Sprints Agiles

La clave de Shift Left es que la seguridad no espera al sprint de pruebas. Cada sprint tiene actividades de seguridad especificas y proporcionales al riesgo del componente que se esta construyendo.

SprintActividadSeguridad aplicada
Sprint 1Diseno del modulo de autenticacionDefinir politica de credenciales: nunca en el codigo fuente. Usar variables de entorno o gestores de secretos (HashiCorp Vault).
Sprint 2Implementacion del loginRevisar con SAST — SonarQube, Semgrep — que no existan strings con credenciales. Configurar regla en el pipeline CI/CD.
Sprint 3Pruebas del sistemaDAST con OWASP ZAP: intentar login con credenciales conocidas. Verificar que los logs no contengan contrasenas en texto plano.
Sprint 4Revision pre-entregaCode review en gestion de secretos. Verificar que .env esta en .gitignore. Auditoria de permisos.
Sprint 5Monitoreo post-despliegueVerificar que ningun log exponga contrasenas. Alertas ante intentos fallidos. Rotacion de credenciales con Vault.

LoginServlet.java — version seguraSeguro
// Credenciales desde variables de entorno, no hardcodeadas
private static final String ADMIN_USER = System.getenv("APP_ADMIN_USER");
private static final String ADMIN_HASH = System.getenv("APP_ADMIN_HASH"); // bcrypt hash

// Rate limiting por IP (max 5 intentos / 15 min)
LoadingCache<String, Integer> loginAttempts = CacheBuilder.newBuilder()
    .expireAfterWrite(15, TimeUnit.MINUTES)
    .build(CacheLoader.from(k -> 0));

protected void doPost(HttpServletRequest req, HttpServletResponse res) {
    String user = req.getParameter("user");
    String pass = req.getParameter("pass");
    String ip   = req.getRemoteAddr();

    // Log sin datos sensibles, solo IP y timestamp
    logger.info("Login attempt from IP: {}", ip);

    // Bloqueo tras 5 intentos fallidos
    if (loginAttempts.get(ip) >= 5) {
        res.sendError(429, "Demasiados intentos. Intente mas tarde.");
        return;
    }

    // Comparacion con hash bcrypt, nunca texto plano
    boolean valid = user.equals(ADMIN_USER) && BCrypt.checkpw(pass, ADMIN_HASH);

    if (valid) {
        // Regenerar sesion para prevenir session fixation
        req.getSession(false).invalidate();
        req.getSession(true).setAttribute("user", user);
        res.sendRedirect("dashboard.jsp");
    } else {
        loginAttempts.put(ip, loginAttempts.get(ip) + 1);
        // Mensaje generico, no revela que campo fallo
        res.sendError(401, "Credenciales invalidas.");
    }
}
Mejoras aplicadas — Principio Shift Left Security
Credenciales movidas a variables de entorno (System.getenv()) — eliminado el hardcoding desde el Sprint 1.
Contrasena almacenada como hash bcrypt — nunca se compara texto plano contra texto plano.
Log de auditoria que solo registra la IP, nunca el username ni la contrasena.
Rate limiting por IP con ventana de 15 minutos — defensa ante fuerza bruta automatizada.
Regeneracion del ID de sesion al autenticar — previene session fixation attack.
Mensaje de error generico — no revela cual campo (usuario o contrasena) es incorrecto.
Estas reglas se validan automaticamente con SonarQube/Semgrep en cada commit del pipeline CI/CD.
06 — Pensamiento critico

Reflexion critica

“La seguridad no se anade al software… Se disena desde el primer momento en que se piensa el sistema.”

— Lic. Eliecer Castillo Bravo, Docente ULEAM
El rol del ingeniero de software

Este ejercicio nos hace reflexionar sobre algo que los libros de texto no siempre enfatizan: el ingeniero que escribe pass.equals("1234") probablemente no penso en las consecuencias. No porque sea negligente, sino porque la cultura del equipo o el apuro del sprint no le recordo que esa decision tiene consecuencias reales. La responsabilidad de la seguridad no es del equipo de QA ni del arquitecto: empieza en quien escribe la primera linea de codigo.

Limitaciones de las herramientas

Una herramienta SAST como SonarQube puede detectar que hay una contrasena hardcodeada, pero no puede entender el contexto organizacional: por que se tomo esa decision? Era un parche temporal que nadie elimino? La automatizacion resuelve la deteccion, pero la cultura de seguridad es lo que resuelve la raiz del problema. Un equipo que entiende el riesgo no necesita que la herramienta le grite.

Relacion con decisiones de diseno

Los tres problemas del codigo (credenciales hardcodeadas, log inseguro, ausencia de rate limiting) podrian haberse prevenido con decisiones tomadas en la fase de diseno, antes de escribir una sola linea de codigo. Un threat model basico de 30 minutos habria identificado “que pasa si alguien accede al repositorio?” como una amenaza real. Eso es exactamente lo que propone Shift Left: no es una tecnica de testing, es una forma de pensar el software desde el principio.

“Las herramientas detectan sintomas. La cultura cura la enfermedad.”

— Reflexion del equipo de analisis, ULEAM 2026
